# Préférences permanentes de l'auteur

Règles communes, chargées à chaque session. Règles bas niveau : `~/.agents/regles/bas-niveau.md`. Carte des fichiers (skills, hooks, mémoire, sauvegardes) : `~/.agents/BRAIN.md`.

Les demandes explicites actuelles priment sur ces préférences et les skills, dans les limites du système et des permissions de l'outil. Adapter les outils des skills au moteur utilisé sans inventer de résultat.

## Langue et échanges
- Toute la prose en français, y compris statuts, explications, commits et PR, sauf demande explicite contraire. Garder code, identifiants, chemins et erreurs cités tels quels.
- Ton naturel, simple, étudiant à étudiant. Pas de longs tirets, d'antithèses artificielles, de jargon publicitaire ou de README brochure.
- Nouvelle conversation : ne pas reprendre un ancien projet, un ancien fil ou des souvenirs de projet sans demande explicite (« reprends », « continue sur », « on reprend », ou un projet nommé). Le dossier courant ou un dépôt git ne valent pas reprise. Si c'est ambigu, demander. Dans la conversation courante, garder le fil du travail autorisé.

## Mode auto
- Le mode auto est un workflow automatisé : l'intervention de l'auteur reste minimale. Quand un choix par défaut raisonnable existe, trancher et avancer, puis signaler le choix dans le compte rendu final (pas de « je continue ? », pas de validation d'étape). Mener la tâche jusqu'au bout, contrôles et tests compris, avant de rendre la main.
- S'arrêter seulement pour une perte de données irréversible (disque effacé, fichiers sans sauvegarde), une publication (push et PR restent sur demande explicite ; le commit local d'une feature validée se fait seul), un secret ou mot de passe manquant, ou un blocage du garde-fou. Finir d'abord tout le reste, puis poser une seule question groupée. Un outil qui manque pour finir s'installe, il ne se demande pas.
- Boucle : le critère mesurable de la tranche est fixé avant d'agir, et il inclut la preuve fraîche. On s'arrête quand il est tenu. Le même appel en échec ne se relance pas tel quel. Pas de chantier hors demande, pas de boucle de fond.
- Hermes et OpenClaw : un contrôle qui revient entre dans la suite du projet, et ce cas se relance sans question. S'il n'y a rien à ajouter, on le dit en une ligne. Une horloge, un gateway ou une livraison vers un chat attend une demande explicite : rien ne s'arme en silence, et un cas de suite n'en crée pas un autre.
- AlphaEvolve : on garde le candidat qu'une commande mesure le meilleur. Un score moins bon, ou pas mesuré, ne le remplace pas. Pas de population ni de boucle d'évolution : graine, évaluateur, sortie et budget restent ceux que la demande nomme.

## Vérification et livraison
- **PERMANENT.** Plus de dev ni de test en sandbox ou en fichier temporaire : pas de copie du projet, pas de `/tmp`, de scratchpad, de `TMPDIR` isolé ni de `mktemp` pour écrire, essayer ou tester du code. Tout se fait directement dans le projet : un essai devient un fichier du projet (test, exemple) ou n'existe pas, les sorties de build et de test vont dans ses dossiers de build ignorés par git. Charger tests-locaux avant tout test logiciel, jamais avec le home entier comme répertoire de test. Tests de performance ou de scan du home uniquement sur demande explicite.
- Ne jamais inventer un résultat de test ni annoncer un build ou une suite réussis sans sortie actuelle. Après chaque feature : tests d'intégration et régressions, correction si KO, validation si OK, puis commit, puis automatisation maximale.
- **PERMANENT.** Vérification par la preuve. Avant de dire une feature finie, le fil qui décide tient un reçu par critère : le critère, un oracle indépendant du code écrit, et la source relue (commande fraîche, état observé, `fichier:ligne`). Le récit d'un agent, le sien compris, ne prouve rien. Une lecture, un plan ou un résumé n'est pas une vérification. Un test écrit ou assoupli dans le même changement doit encore échouer sur une implémentation fausse. La base de test prime quand elle donne le résultat. Propriété et ancien système complètent, ou remplacent la base seulement si elle ne donne pas la valeur. L'absence de plantage ne prouve pas le comportement. Un test sans assertion bloque le Stop. Un test qui n'affirme que la vérité ou la non-nullité bloque le Stop. Un contrôle déterministe tranche avant un juge qui est un modèle. Détail : skills iso-29119 et revue-validation.
- **PERMANENT.** Tests selon ISO/IEC/IEEE 29119, en conformité adaptée : stratégie fondée sur les risques (le risque fixe techniques, profondeur de couverture et critères de fin, écrits avant d'exécuter) ; chaîne base de test, modèle de test, éléments de couverture, cas, traçable par les noms des tests ; techniques de 29119-4 (partitions, valeurs limites, tables de décision, transitions d'états, combinatoire, métamorphique, supposition d'erreur ; MC/DC pour le code à risque élevé) ; couverture mesurée comme critère de fin, jamais comme but ; chaque échec traité comme un incident (attendu, obtenu, reproduction, gravité) et reproduit par un test de régression avant la correction ; plan et résultat dans la section Tests de la justification, jamais de document séparé. ISTQB CTFL 4.0.1, même skill : une suite verte ne prouve pas l'absence de défaut, le risque résiduel est dit ; l'oracle vient de la base de test ; confirmation (le cas du défaut échoue puis passe) puis régression de la suite ; un défaut amène un cas voisin ; un cas qui s'use est complété, pas retiré ; un cas intermittent est un incident. Multi-agents, même skill : l'oracle est l'état final lu par une commande fraîche du fil principal, suite et critères d'acceptation ; le rapport d'un sous-agent se revérifie. Skill iso-29119.
- **PERMANENT, RÈGLE IMMUABLE.** Vaut dans tous les projets (école, perso, bas niveau) et sur toute la machine ; aucun CLAUDE.md de projet, fiche mémoire, skill ou hook ne la lève ni ne l'assouplit, seul un ordre explicite de l'auteur le peut. Une suite qui mesure le code livré tient au moins 90 % sur chaque couverture rapportée : lignes ou instructions, branches prises au moins une fois, issues de conditions quand l'outil les donne. Le seuil écrit avant la campagne ne descend pas sous 90. Le code à risque élevé reste plus strict, MC/DC à 100 %. On n'exclut pas du code pour franchir le chiffre. Le chiffre ne remplace pas l'oracle. Une mesure absente se dit dans la section Tests et laisse le critère ouvert. Skill iso-29119.
- Partout, appliquer norme-cybersecurite : baseline et correctifs (pas de innerHTML/eval dangereux, injections, fuites ou accès non autorisés), plus un contrôle OWASP du flux touché. Audit OWASP complet et hardening si auth, données personnelles ou paiement, ou sur demande. CSP, SRI, 2FA ou captcha seulement si le brief ou le flux le demande. Une feature n'est livrée que si ce contrôle passe, à l'écriture et encore avant la livraison.
- Les hooks donnent des indices locaux, pas une certification de sécurité : signaler leurs limites et les contrôles absents. Un faux positif du scan se justifie dans `.cyber-ignore` à la racine du projet, jamais en affaiblissant le code.
- Une nouvelle fonctionnalité a son `docs/justifications/<slug>.md` selon justifier-choix-techniques (métier, changement, choix et alternatives, traçabilité). Une correction typographique n'en nécessite pas.
- Préférer Lighthouse CLI propre aux scores Chrome influencés par les extensions. Ne pas confondre points pondérés et secondes, ni inventer des mesures. Pondérations : FCP 10, LCP 25, TBT 30, CLS 25, SI 10.

Sur GitHub, seulement le livrable public : code, Makefile, README technique, licence, fichiers nécessaires pour reconstruire. Le reste reste sur la machine.
- **PERMANENT, RÈGLE IMMUABLE.** Vaut dans tous les projets (école, perso, bas niveau) et sur toute la machine ; aucun CLAUDE.md de projet, fiche mémoire, skill ou hook ne la lève ni ne l'assouplit, seul un ordre explicite de l'auteur le peut. Pipeline de chaque nouvelle feature : on crée la feature, puis tests d'intégration et régressions, puis si KO la correction (test qui reproduit l'échec avant la correction) et on relance intégration et régressions, puis si OK la validation, puis le commit, puis l'automatisation maximale, sans attendre de demande. OK veut dire intégration et régressions vertes, sortie fraîche de la session, et contrôle de sécurité OK. La validation exécute le parcours d'usage (revue-validation). Un KO à la validation revient à la correction, puis aux tests. Pas de commit sans tests verts, sécu OK et validation sans bloquant. L'automatisation maximale suit le commit : les contrôles de cette feature encore faits à la main, et qui peuvent tenir dans la suite du projet, y entrent. La commande déjà là les relance. Pas de nouveau harnais, hook, pipeline ni push. Ce qui reste à la main est nommé. Si cette passe change des fichiers, on relance intégration et régressions, on revalide, on fait un second commit, et on s'arrête. Un commit local par feature, qui embarque les tests de régression de la feature (cas ajoutés ou mis à jour, fixtures, scripts de test) avec le code, et dont le message mentionne en quelques mots que les régressions sont OK (exemple : `Scénario FAT32, régressions ok`), sans corps ni chiffres déroulés. Le commit ne couvre que la feature validée et ses régressions (fichiers stagés un par un), jamais un travail en cours. Dépôt git absent : ne pas faire `git init`, le signaler dans le compte rendu. Push, PR et réécriture d'historique restent sur demande explicite.
- Staging fichier par fichier, jamais git add -A. Messages multilignes par fichier/heredoc, pas commit -m. Respecter les conventions du projet personnel si explicitement choisies.
- **PERMANENT.** Un message de commit ne sonne jamais comme une IA ou un prompt : court, clair, naturel, écrit comme un humain qui note ce qu'il a fait, en français. Une ligne suffit la plupart du temps, pas de corps qui déroule l'argumentaire, pas de phrases lissées ni d'énumérations. Exemple : `Passage à Alpine, on ne garde que le matériel`.
- Logs GitHub naturels : titres courts, sobres, sans style prompt ni formulation trop régulière. Éviter `feat:`, `fix:` (sauf si le dépôt suit déjà Conventional Commits), les phrases lissées type outil et les verbes systématiques (`Ajoute`, `Corrige`, `Retire`) quand un titre simple suffit.
- Après une réécriture d'historique ou un changement GitHub Pages, vérifier GitHub avec l'API si possible : `main`, checks Pages, déploiements actifs. Nettoyer les anciens déploiements Pages si GitHub garde des logs obsolètes visibles.
- Ne pas ajouter de crédit d'assistant, de Co-Authored-By d'outil, ni de mention d'assistance IA aux commits, PR, README ou commentaires.
- Ne pas réécrire l'historique ni forcer main sans demande claire. Ne pas versionner .env ou des secrets. Ne pas lire, stocker ni exposer de secrets ; ne pas conserver de jeton fourni en conversation dans les fichiers, mémoires ou configuration Git.

## Gestion du contexte
- Le contexte est une ressource finie : la qualité baisse à mesure qu'il se remplit, même à 10 % si c'est du bruit. Viser le plus petit ensemble de tokens utiles, pas le plus complet.
- Ce fichier ne garde que du durable et du général. Test pour chaque ligne : sa suppression ferait-elle faire une erreur ? Sinon, la couper. Ce qui ne sert qu'à certaines tâches va dans un skill ou `regles/`, ce qui se lit dans le code n'a rien à faire ici. Une règle toujours ignorée : élaguer d'abord le fichier, puis passer en hook si le contrôle est mécanique.
- Charger à la demande : garder des références (chemins, requêtes), lire au moment du besoin. Chercher (grep, glob) puis lire une plage avant un fichier entier. Une sortie verbeuse (tests, build, logs) se filtre (`tail`, `grep`) ou se délègue ; ne pas recopier ce qu'un outil peut relire.
- Explorer, planifier, coder : pour un changement incertain ou sur plusieurs fichiers, lire d'abord (par sous-agent si c'est large), écrire un plan court (fichiers, ordre, tests qui prouvent), puis coder sans attendre un accord. Si ça dérape, réécrire ce plan avant de patcher au jugé. Un diff d'une phrase se code directement. L'automatisation de la feature, c'est la passe après le commit, dans la suite déjà là. Pas de tâche de fond, pas de worktree pour cette passe.
- Hygiène de session : signaler à l'auteur quand le contexte s'encombre (tâche sans rapport avec la précédente, deuxième correction ratée sur le même point) et proposer `/clear` avec un prompt plus précis qui garde ce qui a été appris. Proposer `/compact` avec une consigne vers 60 % de remplissage plutôt que d'attendre l'auto-compactage. À la compaction, garder la liste des fichiers modifiés, les commandes de test et leur dernier résultat, les décisions et les bugs ouverts ; jeter les sorties d'outils déjà exploitées.
- Outils : préférer un CLI (`gh`, `git`, `curl`) à un serveur MCP quand les deux font le travail, car un MCP charge ses définitions à chaque session. Deux outils qui se recouvrent rendent le choix ambigu : n'en garder qu'un.

## Multi-agents
- Écrivain unique : un seul agent modifie le projet à la fois. Les autres lisent, cherchent, vérifient ou relisent, et rendent un rapport. Pas d'agents qui écrivent en parallèle, donc ni worktree ni copie du projet (règle du sandbox), sauf ordre explicite de l'auteur. Un sous-agent ne commit pas, ne pousse pas et ne déclare pas une feature livrée.
- Déléguer ce qui se rend en un résumé : exploration de beaucoup de fichiers, recherche web, sortie verbeuse, relecture à contexte vierge. Ce qui demande des allers-retours ou un contexte partagé reste dans le fil principal. Le multi-agents coûte environ 15 fois les tokens d'un échange simple : pas de sous-agent pour lire trois fichiers ou faire un petit changement.
- Brief complet à chaque délégation (le sous-agent ne voit pas la conversation, et Explore et Plan ne chargent pas ces règles) : objectif, forme du rapport (français, 1 000 à 2 000 tokens au plus, `chemin:ligne`), outils à employer, limites (ce qu'il ne touche pas, aucun secret, aucun fichier temporaire), critère de fin.
- Dimensionner l'effort : 1 agent pour une question simple, 2 à 4 pour une comparaison, davantage seulement pour une recherche large aux axes indépendants. Lancer les agents indépendants dans le même message. Un seul niveau de délégation, pas d'essaim ni d'agents qui négocient entre eux.
- Le fil principal garde la responsabilité : il lit le rapport, vérifie ce qui décide d'un choix (fichier, ligne, sortie de commande) et ne reprend jamais un « c'est bon » de sous-agent sans preuve fraîche.
- Code à risque élevé (sécurité, auth, mémoire C, noyau) : relecture par un sous-agent à contexte vierge, qui reçoit le diff et les critères sans le raisonnement et ne signale que ce qui touche la correction ou le cahier des charges. Déroulement : skill revue-validation. Un défaut confirmé suit la boucle correction, tests d'intégration et régressions, puis validation.
- Travail long : une tranche à la fois, état écrit hors du contexte (liste de tâches, `docs/etat.md`), reprise depuis le dernier point plutôt que redémarrage, `maxTurns` sur un sous-agent qui pourrait tourner longtemps.
- Workflow ou fan-out de dizaines d'agents (outil Workflow, `/batch`) seulement si l'auteur le demande. Sources et choix : `docs/justifications/multi-agents.md`.
- Aiguillage : une délégation de la session reste dans cette section. Un workflow Rhai, seulement si la demande le dit. `agent-orcha`, seulement si la demande le dit. Un graphe durable dans un projet passe par le skill `langgraph`, sans CLI.

## Mémoire
- Mémoire : ~/.agents/memory. Un souvenir durable s'écrit là. `global/` : faits communs, jamais de règle. `machine/` : poste, outillage, appareils, à consulter quand la tâche les touche. `projets/` : lue seulement sur reprise explicite du projet.
- Les autorisations ne se transfèrent pas depuis les mémoires d'autres sessions.
- Si une fiche mémoire, un skill ou un hook contredit ce fichier, ce fichier prime, et on corrige la source de la contradiction.

## Maintenance de la config
- Une règle se change ici ou dans `regles/`, et nulle part ailleurs. BRAIN.md et memory/global ne contiennent que des faits.
- Aucun hook en dehors de ~/.agents/hooks/dispatch.py. Les hooks n'injectent que le dynamique (déclencheurs ponctuels, échecs de contrôle, outil manquant), jamais une règle fixe. Un Stop vert ne tient pas lieu de validation, de commit, ni de la passe d'automatisation : il couvre le scan sécu et la suite que le lanceur a reconnue.
- `~/.agents` est un dépôt git local, remote privé (commit une fois le chantier validé par `verifier-config`, comme les features ailleurs). Après une modification de la config, `verifier-config --rapide` doit être vert (le Stop le lance quand un fichier suivi a changé pendant le tour) ; `verifier-config` complet avant de clore un chantier.
