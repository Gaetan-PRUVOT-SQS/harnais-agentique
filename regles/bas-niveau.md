# Règles des projets bas niveau

S'ajoutent à `~/.agents/AGENTS.md` pour les projets OS, noyau, bootloader,
pilotes, libc, shell maison et Unix-like (VelumOS, sqscore, etc.). Le
CLAUDE.md du projet les importe avec `@~/.agents/regles/bas-niveau.md`.

- Bas niveau et OS from scratch (noyau, bootloader, pilotes). Projet en cours : VelumOS (`~/Bureau/VelumOS/VelumOS`), « Fast by design. Private by default. », OS libre from scratch en C ou en assembleur, pour x86 et ARM en 32 et 64 bits (plus RISC-V), PC anciens et récents, portables et fixes, inspiré de KolibriOS pour sa frugalité (on ne développe pas KolibriOS, ses sources servent de référence, sans copie de code GPL), format d'appli maison. Fast : le moins gourmand possible, optimisation maximale mais toujours mesurée avant/après (skill os-efficience, `make mesure`). Private : aucun pistage, moindre privilège, isolation, rien ne sort sans accord (skill os-confidentialite), chaque engagement prouvé par un test (`docs/charte.md`). Cœur portable en C dans `kernel/`, spécifique dans `arch/<arch>/` ; `make test-all` couvre toutes les cibles ; C par défaut, asm là où le C ne peut pas ou là où la mesure montre un gain, avec sa version C de référence dans les tests. Projet sans dépôt git : poser `.mode-side-project` à la racine pour que les hooks en trouvent la racine. Chaque étape se prouve dans QEMU (sortie série, gdb), jamais « ça devrait booter ». Par défaut en mode coach, le but étant d'apprendre : l'auteur écrit le cœur (GDT, IDT, gestion mémoire, paging, ordonnanceur, appels système, logique des applis asm) ; l'agent explique, relit, débogue et écrit l'échafaudage (Makefile, scripts de test, stubs asm répétitifs). Binôme ou code complet par l'agent seulement sur demande explicite.
- **PERMANENT.** Intégration système et matériel (VelumOS, pilotes, tout bas niveau) : la spec ou la datasheet fait foi, sa section est citée dans la justification ; le matériel se découvre (CPUID, ACPI, PCI, device tree), jamais d'adresse, d'IRQ ou de fonction CPU supposée ; toute attente sur le matériel a un timeout en temps réel ; chaque interface entre couches (boot, appels système, format d'appli, disque) est versionnée et testée des deux côtés ; build reproductible (versions et sha256 épinglés, build-id affiché au boot). Preuve par paliers : hôte, faux périphérique, QEMU sur chaque arch et ses variantes, puis vraie machine pour ce qui touche un pilote, le firmware ou le boot, résultat noté dans `docs/materiel.md`. Sur vraie machine : clé écrite seulement avec `ecrire-image` (cible par `/dev/disk/by-id`), aucune écriture sur un disque interne avant tous les tests sur image, jamais de flash firmware ni d'écriture de variables EFI depuis l'OS en développement, UART en 3,3 V. Skills pilotes-materiel et integration-systeme.
- **PERMANENT.** Noyau (VelumOS, tout noyau) : invariants écrits et vérifiés (`kassert`), profils debug (UBSan en piège, poison, vérifications coûteuses) et release, durcis et testés tous les deux ; jamais de panique sur une entrée d'appli ni sur du matériel absent ; chaque donnée partagée a son verrou nommé, ordre des verrous écrit, rien de bloquant sous spinlock ; pointeurs user d'un type à part, ouverts par une seule fonction de copie. Sécurité : drapeaux du gabarit osdev-c (canari, locales à zéro, registres effacés, UBSan en debug) prouvés par `make test`, W^X, NX, SMEP, SMAP et UMIP si le CPU les a, pages de garde et double fault sur sa pile, indices user masqués contre la spéculation, mitigations choisies selon le CPU détecté et annoncées au boot. Optimisation noyau toujours mesurée avant/après (os-efficience) et jamais au prix d'une protection sans chiffre. Skills noyau-conception, noyau-securite, os-efficience.
- **PERMANENT.** Mémoire d'un OS : chaque allocation a un propriétaire et des compteurs ; budget mémoire écrit poste par poste (image, tables de pages, tas, framebuffer, piles, applis) et mesuré, RAM minimale par `os-mesure ram`, dépassement visible au test et relevé seulement avec son chiffre ; carte RAM du firmware normalisée, zones basses préservées, jamais d'ACPI NVS ni de réservé réutilisé ; carte d'adresses virtuelle écrite par arch ; toute allocation peut échouer et son chemin d'échec est testé (épuisement, noyau vivant) ; mémoire des applis déclarée, plafonnée, donnée à zéro, reprise à la sortie, sans surengagement ; jamais deux types de cache sur une même page physique ; RAM d'une machine instable testée (memtest86+) avant d'accuser le noyau. Skill gestion-memoire.
- **PERMANENT.** Shell maison : grammaire écrite, étages testables seuls, comportement prouvé contre dash (`compare-shells`). Système maison : rien de tiers livré sans déclaration REUSE, `licences-tierces` avant chaque livraison (sans `--autorisees`, l'objectif est zéro code tiers), clean room depuis les specs, jamais de code copié ni paraphrasé, « de type Unix » et jamais « Unix ». Skills shell-maison, systeme-maison.
- **PERMANENT.** Unix-like maison : partir du gabarit `systeme-maison/templates/unix-like-i686` (noyau, libc, `/init`, initrd, image disque, `make test` en BIOS et UEFI) ; ABI (numéros d'appels, erreurs) en source unique partagée par noyau et libc ; chaque sous-système (processus, fichiers, terminal, libc, réseau) prouvé par des programmes de test en mode utilisateur jugés par `qemu-test`, et comparé au comportement de l'hôte ; images fabriquées par `image-disque` et relues par les outils de l'hôte (`debugfs`, `e2fsck`, `tcpdump`) ; tout paquet, table firmware, image disque ou descripteur USB est une entrée hostile ; réseau éteint et rien à l'écoute par défaut. Skills processus-unix, fichiers-unix, terminal-unix, libc-maison, pile-reseau.
- **PERMANENT.** POSIX.1-2024 fait foi aussi pour le shell maison, la libc et le noyau de type Unix : shell maison et libc maison comparés à dash et à la glibc, ERRORS « shall fail » changées en cas de test, sous-ensemble et valeurs implementation-defined écrits (document de conformité) ; libc vérifiée par `verifier-posix` (noms d'erreurs, prototypes) ; « compatible avec un sous-ensemble de POSIX », jamais « conforme » sans certification. Skill posix.
- **PERMANENT.** Pratiques Unix, FreeBSD et Linux, reprises par leurs manuels, docs et livres, jamais par leur code : avant toute interface, lire ce que FreeBSD et Linux ont fait et dû corriger ; ABI utilisateur jamais cassée (numéro jamais réutilisé, nouvel appel plutôt que sens changé, bit de drapeau inconnu refusé par `EINVAL`, structure extensible passée avec sa taille, types 64 bits pour temps, tailles et inodes dès le départ, numéro d'ABI dans chaque binaire) ; descripteurs plutôt que noms globaux (poignée de processus, `O_CLOEXEC` par défaut, appels `*at` et résolution bornée) ; moindre privilège par droits sur les descripteurs (Capsicum) ; outils à la Unix (une tâche, données sur stdout, diagnostics sur stderr, codes de sortie, erreurs d'écriture vérifiées) et page de manuel mdoc vérifiée par `mandoc -T lint` avec chaque interface ; noyau debug outillé comme FreeBSD et Linux (assertions, ordre des verrous, allocations typées qui disent si elles peuvent attendre, injection de fautes) ; système de base cohérent en un dépôt ; aucune régression tolérée. Skill unix-freebsd-linux.
- **PERMANENT.** Agents sur un projet OS (complète la section Multi-agents d'AGENTS.md, gabarit `docs/brief-agent.md` du projet, sources dans `docs/justifications/multi-agents.md`) : écrivains en parallèle seulement sur ordre explicite de l'auteur, 3 à 5 par vague, dans l'ordre des dépendances (contrats et ABI, noyau, bibliothèques, applis, tests et docs, relecture). Périmètre disjoint écrit dans le brief, un propriétaire par fichier central (en-têtes partagés, table d'appels, Makefile, linker script) ; les autres demandent la modification dans leur rapport. Contrats complets avant la vague (représentations, erreurs, propriété mémoire) et journal des changements d'interface lu avant chaque build. Attendus venus d'un oracle indépendant avec sa provenance, jamais de la sortie du code ; un agent ne touche ni aux tests hors périmètre, ni aux assertions, drapeaux de sanitizers ou `-Werror`, et n'ajoute ni `#if 0` ni test sauté : test ou spec contradictoire, il s'arrête et le signale. Constante matérielle sans section de spec citée : « non vérifié » au rapport. Rapport structuré (fichiers, commandes avec code de sortie et dernières lignes, non vérifié, hors périmètre) que le fil principal recontrôle en relançant les commandes ; un défaut de relecture n'est recevable qu'avec un test rouge ou une citation. QEMU et gros builds sous `flock`, un dossier de build par agent. Sans git : instantané `tar` et sha256 avant chaque vague.
